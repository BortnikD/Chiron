# Документация API Chiron

Спецификация OpenAPI генерируется из кода бэкенда (springdoc-openapi): описания эндпоинтов берутся из аннотаций
`@Operation` и `@Tag` в контроллерах. Этот файл описывает работу с API и основные сценарии;
полный список маршрутов, параметров и схем запросов/ответов смотрите в OpenAPI.

## Как открыть

Сначала запустите бэкенд по [инструкции в README](../chiron/README.md#локальный-запуск)
с профилем `local`. По умолчанию он слушает порт `8080`; в демо используйте порт `8081` во всех адресах ниже.

| Вариант | Адрес | Когда использовать |
|---|---|---|
| **Scalar** | http://localhost:8080/scalar.html | Основной вариант: удобный поиск, примеры запросов на разных языках, отправка запросов из браузера. Загружается с CDN, нужен интернет |
| **Swagger UI** | http://localhost:8080/swagger-ui.html | Классический интерфейс; работает без интернета |
| **OpenAPI JSON** | http://localhost:8080/v3/api-docs | Сырая спецификация: импорт в Postman / Insomnia / Bruno, генерация клиента для фронтенда |
| **Use case диаграмма** | [`docs/usecase.excalidraw`](./usecase.excalidraw) | Открыть на https://excalidraw.com (Open → выбрать файл) или в VS Code с расширением Excalidraw |

Документация (`/scalar.html`, `/swagger-ui.html`, `/v3/api-docs`, `/v3/api-docs.yaml`) доступна без авторизации только в `local`.
В `production` и без активного профиля генерация спецификации отключена, а доступ к документации запрещён,
в том числе авторизованным пользователям. Если одновременно включены `local` и `production`, доступ также закрыт.

## Проверка состояния (health check)

Эндпоинты Spring Boot Actuator. Доступны **без токена**, только `GET`. В документации они в группе `Actuator`.

| Эндпоинт | Что проверяет | Когда использовать |
|---|---|---|
| `GET /actuator/health` | Приложение, база данных и бакет фотографий | Общая проверка «бэкенд работает»: индикатор на фронтенде, мониторинг |
| `GET /actuator/health/readiness` | Приложение запущено, база данных и бакет фотографий доступны | Можно ли уже отправлять запросы (используется в healthcheck Docker Compose) |
| `GET /actuator/health/liveness` | Процесс приложения жив (базу **не** проверяет) | Нужно ли перезапускать контейнер |

Ответ **не** обёрнут в `ApiResponse`. Подробности о компонентах (версия БД, место на диске и т. п.) не
отдаются, только итоговый статус:

```json
{ "status": "UP" }
```

| HTTP-статус | `status` | Значение |
|---|---|---|
| `200` | `UP` | Всё работает |
| `503` | `DOWN` / `OUT_OF_SERVICE` | Бэкенд запущен, но не готов, например недоступна база данных |
| нет ответа / сетевая ошибка | — | Бэкенд не запущен или недоступен по сети |

Пример проверки на фронтенде:

```ts
export async function isBackendHealthy(): Promise<boolean> {
  try {
    const response = await fetch("http://localhost:8080/actuator/health", {
      signal: AbortSignal.timeout(3000),
    });
    // 503 comes with a JSON body too, so checking response.ok is enough.
    return response.ok;
  } catch {
    // Network error or timeout: the backend is not reachable.
    return false;
  }
}
```

CORS для этих эндпоинтов настроен так же, как для остального API (origin'ы из `cors.allowed-origins`).

## Авторизация

API использует JWT-токен. Токен один и живёт 30 дней, refresh-токена нет.

1. Получите токен:
   - `POST /api/v1/auth/register` — регистрация, всегда создаёт пользователя с ролью `CLIENT`;
   - `POST /api/v1/auth/login` — вход по email и паролю.
2. Возьмите `result.accessToken` из ответа.
3. Передавайте его в заголовке `Authorization: Bearer <token>`.
   - В Scalar: блок **Authentication** → `bearerAuth` → вставить токен.
   - В Swagger UI: кнопка **Authorize** → вставить токен (без слова `Bearer`).
4. `GET /api/v1/users/me` — проверить, под кем вы авторизованы; `PATCH /api/v1/users/me` — изменить свои данные
   (имя, отчество, фамилию, email, телефон). `fullName` сервер собирает сам в формате `И. О. Фамилия`.

Первый администратор создаётся при старте приложения из переменных окружения `ADMIN_*`, если email ещё не занят.
Для Compose они задаются в корневом `.env` (шаблон — [`.env.example`](../.env.example)) или `.env.production`
(шаблон — [`.env.production.example`](../.env.production.example)); демо использует значения из Compose.
При запуске из IDE / Java передайте переменные процессу: Spring Boot сам `.env` не читает.
Изменение `ADMIN_*` не обновляет существующий аккаунт. Ветеринаров и других администраторов создаёт администратор через
`POST /api/v1/admin/users`.

## Что куда

Эндпоинты разделены по ролям. Раздел в документации соответствует префиксу URL, а группы (теги) подписаны
префиксом роли.

| Префикс | Доступ | Группы в документации | Что внутри |
|---|---|---|---|
| `/api/v1/auth` | всем | `Auth` | Регистрация и вход |
| `/api/v1/users/me` | любая роль, с токеном | `Users` | Просмотр и изменение своих данных |
| `/api/v1/notifications`, `/ws` | любая роль, с токеном | `Notifications` | Свои уведомления: список, счётчик непрочитанных, отметка о прочтении; получение новых в реальном времени по STOMP |
| Публичные GET (перечень ниже) | всем, без токена | `Species`, `Specializations`, `Services`, `Service species`, `Veterinarians`, `Veterinarian species permissions`, `Work schedules`, `Schedule exceptions`, `Appointments` | Справочники клиники: виды животных, специализации, услуги и их цены по видам, врачи и какие виды они лечат, расписание врачей, поиск свободных слотов и проверка слота |
| `/api/v1/client/...` | `CLIENT` | `Client: Pets`, `Client: Appointments`, `Client: Vaccinations`, `Client: Summary` | Свои питомцы; запись на приём, список и отмена своих записей; прививки своих питомцев и сводка кабинета |
| `/api/v1/veterinarian/...` | `VETERINARIAN` | `Veterinarian: Profile`, `Veterinarian: Appointments`, `Veterinarian: Pets`, `Veterinarian: Vaccinations` | Свой профиль врача (просмотр, изменение описания, фото и стажа); свои записи — смена статуса, заметки врача и назначение повторного приёма; пациенты (питомцы, у которых была запись к этому врачу) и их прививки |
| `/api/v1/admin/...` | `ADMIN` | `Admin: *` | Полное управление: пользователи, питомцы, записи, прививки, врачи и их допуски к видам, расписания и исключения из расписания, справочники; статистика клиники |

Без токена доступны GET к `/api/v1/species/**`, `/api/v1/specializations/**`, `/api/v1/services/**`,
`/api/v1/veterinarians/**`, `/api/v1/work-schedules`, `/api/v1/schedule-exceptions`,
`/api/v1/appointments/slots` и `/api/v1/appointments/availability`.

Роли не образуют иерархию: администратор использует `/admin/...`, а не маршруты клиента или ветеринара.
Клиент видит свои ресурсы, ветеринар — свои записи и доступные ему данные пациентов.
Попытка обратиться к чужому ресурсу обычно возвращает `403`; для чужого уведомления — `404`.
Администратор работает с данными любых пользователей через `/admin/...`.

## Смена пароля

`POST /api/v1/users/me/password` доступен всем авторизованным ролям с Bearer-токеном:

```json
{ "currentPassword": "old-password", "newPassword": "new-password" }
```

Ограничения нового пароля совпадают с регистрацией: минимум 8 символов и максимум 72 байта UTF-8.
Сервер проверяет текущий пароль и сохраняет BCrypt-хеш нового. При успехе возвращается `204` без тела;
при невалидных данных — `400`, при неверном текущем пароле с действующим токеном — `422`
(`InvalidCurrentPasswordException`, поле `currentPassword`). Отсутствующий или истёкший токен даёт `401`.
Ранее выданные JWT остаются действительными до истечения срока: смена пароля их не отзывает.

## Цвета и иконки справочников

Виды животных содержат nullable-поля `color` и `iconKey`, специализации врачей — nullable-поле `color`.
`color` принимает только HEX в формате `#RRGGBB` (регистр букв не важен), регулярное выражение:
`^#[0-9A-Fa-f]{6}$`. Другой формат возвращает `400`. `iconKey` — произвольная строка для фронта.
`null` означает, что фронт использует своё значение по умолчанию; сервер возвращает его без подстановки.

Чтение списков и отдельных записей: `GET /api/v1/species`, `GET /api/v1/species/{id}`,
`GET /api/v1/species/by-name?name=...`, `GET /api/v1/specializations`, `GET /api/v1/specializations/{id}`.
Новые поля также возвращаются после создания и обновления.

Администратор задаёт поля при `POST /api/v1/admin/species` и `POST /api/v1/admin/specializations`.
Если поле не передано или равно `null`, сохраняется `null`. Изменение выполняется через
`PATCH /api/v1/admin/species/{id}` и `PATCH /api/v1/admin/specializations/{id}`:

```json
{ "color": "#3B82F6", "iconKey": "cat" }
```

Для специализации передавайте только `color`. Отсутствующее поле сохраняет прежнее значение,
явный `null` удаляет значение поля: например, `{ "color": null, "iconKey": null }` сбрасывает оформление вида.
Удаление самой записи: `DELETE /api/v1/admin/species/{id}` или
`DELETE /api/v1/admin/specializations/{id}`; существующие ограничения связей сохраняются.
У записей, созданных до миграции, новые поля равны `null`.

## ФИО врача

`VeterinarianResponse` содержит `firstName`, `middleName` (может быть `null`), `lastName` и `fullName`.
Поля читаются из связанного пользователя, поэтому изменение его имени отражается в последующих ответах о враче.
`fullName` сохраняет общий формат отображения `I. M. Lastname`; для полного ФИО доступны отдельные части имени.
Эти поля возвращаются в публичном каталоге и деталях врача, админских ответах и собственном профиле ветеринара,
включая ответы создания и обновления. `userId` и остальные поля сохранены.

## Специализации врача

`VeterinarianResponse` возвращает основную специализацию в `specializationId` и полный список в
`specializationIds`. Основная специализация стоит первой. Фильтр `specializationId` в публичном и
административном списках врачей ищет по всем назначениям.

- `POST /api/v1/admin/veterinarians` принимает прежнее поле `specializationId` или массив
  `specializationIds`. Если передан только массив, его первый элемент становится основной специализацией.
- `PATCH /api/v1/admin/veterinarians/{id}` с `specializationIds` заменяет весь список. Если основную явно
  не указали, сохраняется текущая, когда она есть в новом списке. В остальных случаях основной становится
  первый элемент массива.
- PATCH только с `specializationId` заменяет прежнюю основную специализацию и сохраняет дополнительные.
  PATCH без обоих полей сохраняет назначения. Явный `null` в PATCH обрабатывается как пропуск поля.

Массив должен быть непустым и содержать уникальные ID существующих специализаций. Если переданы оба поля,
`specializationId` должен входить в массив.

## Виды животных у врача

`VeterinarianResponse` содержит `speciesIds` — массив ID видов, которых разрешено лечить врачу.
Без назначенных разрешений возвращается `[]`. Поле доступно в публичном каталоге, деталях врача,
админских ответах и собственном профиле ветеринара. У только что созданного профиля массив пустой;
создание и удаление разрешений отражаются в последующих чтениях.

Список врачей загружает разрешения пакетно, без отдельного запроса на каждого врача.
Фильтр `speciesId` по-прежнему отбирает врачей, но `speciesIds` каждого найденного врача содержит все его виды.

## Цена и длительность услуги для вида животного

`GET /api/v1/services?speciesId=<UUID>` возвращает доступные для вида активные услуги с полями
`effectivePrice` и `effectiveDurationMin`. Каждое поле независимо использует переопределение для вида,
а если оно не задано (`null`) — соответствующее базовое значение. `basePrice` и `baseDurationMin` сохраняются.
`effectiveDurationMin` не включает `bufferAfterMin`.

Без `speciesId` расчётные поля равны `null`. Они также равны `null` в ответах отдельных услуг и админских
операций, где расчёт для вида не запрашивается. Для списка с видом сервер пакетно загружает переопределения,
без отдельного запроса на каждую услугу.

## Прививки питомцев клиента

`GET /api/v1/client/vaccinations` возвращает массив прививок всех питомцев текущего клиента.
Необязательный `petId` ограничивает выборку одним своим питомцем; для чужого питомца возвращается `403`.
Ограничение по владельцу применяется в запросе к БД и при отсутствии `petId`.

Необязательные `nextDueFrom` и `nextDueTo` задают включительные границы `nextDueOn` в формате `YYYY-MM-DD`.
Если указана хотя бы одна граница, прививки без даты ревакцинации не возвращаются.
Обратный диапазон (`nextDueFrom > nextDueTo`) возвращает `400`.

Сортировка: `nextDueOn` по возрастанию, записи без даты — в конце, при равной дате — по `id` по возрастанию.
Ответ остаётся массивом без пагинации. Например, `?nextDueTo=2026-11-08` вернёт все прививки с истёкшим
или наступающим до этой даты сроком, включая саму дату.

## Сортировка записей клиента

`GET /api/v1/client/appointments` принимает необязательный `direction=ASC|DESC`.
По умолчанию сохраняется `ASC`; для истории с новыми записями сверху используйте `direction=DESC`.
Сортировка выполняется в БД по `startAt`, затем по `id` в том же направлении, до применения пагинации.
Фильтры `petId`, `status`, `from`, `to` и ограничение по текущему владельцу сохраняются.

Пример: `GET /api/v1/client/appointments?status=COMPLETED&direction=DESC&page=0&size=20`.

## Пациенты врача

`GET /api/v1/veterinarian/pets` возвращает постраничный список пациентов текущего врача.
Пациент — питомец, у которого есть хотя бы одна запись к этому врачу, независимо от даты и статуса записи.
Повторные приёмы не создают дубли; питомцы других врачей без записи к текущему врачу не попадают в ответ.
Профиль врача определяется по токену, передавать `veterinarianId` не требуется.

Необязательные фильтры: `ownerId`, `speciesId`, `gender`, `isArchived`, `name` (подстрока без учёта регистра).
Без `isArchived` возвращаются и архивные, и неархивные пациенты. Все фильтры объединяются через AND.
Параметры `page` (с 0) и `size` (1–100, по умолчанию 20) и формат страницы описаны ниже.
Элементы `items` имеют формат `PetResponse`, как у `GET /api/v1/veterinarian/pets/{id}`, включая поля фото.
Сортировка: `createdAt`, затем `id`, оба по возрастанию.

Пример: `GET /api/v1/veterinarian/pets?name=Барс&isArchived=false&page=0&size=20`.
Для числа пациентов в профиле достаточно `?page=0&size=1` и поля `result.totalElements`.

Отбор пациентов, фильтрация, подсчёт и пагинация выполняются в БД через подзапрос к приёмам.
На запрос списка выполняется поиск профиля врача, подсчёт пациентов и выборка нужной страницы —
без выгрузки истории приёмов и отдельных запросов для каждого питомца. Миграция `V05` добавляет индекс
`appointment(veterinarian_id, pet_id)` для этой выборки.
Фронтенду следует использовать этот эндпоинт вместо сбора ID из приёмов и последующей загрузки питомцев по одному.

## Порода питомца

Питомец содержит необязательное поле `breed`: строка до 100 символов или `null`.
Поле принимается при создании питомца клиентом и администратором и возвращается в ответах о питомцах,
включая списки пациентов врача. У существующих питомцев после миграции значение `null`.
При частичном обновлении отсутствие `breed` сохраняет прежнее значение, строка заменяет его,
а явный `"breed": null` очищает поле. Порода служит справочной информацией и не влияет на запись и услуги.

## Сводка питомца по запросу

`GET /api/v1/client/pets` и `GET /api/v1/client/pets/{id}` принимают `withSummary`, по умолчанию `false`.
Без флага или с `withSummary=false` формат JSON сохраняется: `summary` отсутствует, дополнительные запросы
к записям и прививкам не выполняются. При `withSummary=true` добавляется объект `summary`:

| Поле | Значение |
|---|---|
| `completedVisits` | Количество записей со статусом `COMPLETED` |
| `appointmentsCount` | Количество всех записей, включая отменённые |
| `vaccinationsCount` | Количество всех записей о прививках |
| `nextAppointment` | Ближайшая запись `PENDING` или `CONFIRMED` с `startAt >= now`: `{id, startAt, serviceIds}`; иначе `null` |
| `nextVaccinationDueOn` | Минимальный актуальный срок ревакцинации, включая просроченные; иначе `null` |
| `hasOverdueVaccination` | Актуальный срок ревакцинации строго раньше сегодняшней даты в часовом поясе клиники |

Более новая прививка с тем же названием без учёта регистра делает срок предыдущей неактуальным.
Если несколько прививок сделаны в один день, их сроки учитываются наравне; это совпадает с правилом уведомлений.
Отсутствие дат ревакцинации даёт `nextVaccinationDueOn=null` и `hasOverdueVaccination=false`, но не подтверждает
полноту вакцинации. Отсутствующие счётчики равны нулю. Для одинакового времени приёма выбирается запись с меньшим `id`.

Сводки рассчитываются пакетно только для выбранных питомцев текущего владельца; `isArchived` продолжает работать.
Связанные услуги ближайших записей загружаются пакетно; количество дополнительных SQL-запросов не растёт
с количеством питомцев, полная история в память не загружается. Для пустого списка дополнительные запросы
не выполняются. Создание и обновление питомцев,
а также API администратора и ветеринара сохраняют прежние ответы.

## Сводка кабинета клиента

`GET /api/v1/client/summary` возвращает показатели текущего клиента в `ApiResponse`:

| Поле | Значение |
|---|---|
| `activePets` | Количество неархивных питомцев |
| `upcomingAppointments` | Количество записей `PENDING` и `CONFIRMED` с `startAt >= now` |
| `completedAppointments` | Количество всех записей `COMPLETED` |
| `vaccinationsDue` | Количество актуальных записей о прививках со сроком до `today + leadDays` включительно, включая просроченные |
| `vaccinationsOverdue` | Из них — количество со сроком строго раньше `today` |
| `unreadNotifications` | Количество непрочитанных уведомлений |
| `nextAppointment` | Ближайшая предстоящая запись в формате `AppointmentResponse`, либо `null` |

Приёмы учитываются и для архивных питомцев: архивирование не отменяет уже назначенные приёмы и не удаляет историю.
Показатели прививок относятся только к неархивным питомцам; старые сроки исключаются при наличии более новой
прививки с тем же названием без учёта регистра, как в сводке питомца. Прививки без срока не учитываются.
`vaccinationsDue` считает записи о прививках, а не питомцев.

Время фиксируется один раз на запрос; `today` определяется в часовом поясе клиники.
Горизонт берётся из `notification.vaccination-due.lead-days` (по умолчанию 7 дней).
Для одинакового времени ближайшего приёма выбирается запись с меньшим `id`.
Пустые показатели равны нулю. Данные ограничены текущим клиентом на уровне SQL.
Количество SQL-запросов не зависит от количества питомцев; полная история в память не выгружается.
Ближайший приём содержит полный массив услуг в новом формате `AppointmentResponse`.

## Типичный сценарий записи на приём

1. `GET /api/v1/services?speciesId=...` — выбрать услуги для вида питомца; цена и длительность уже рассчитаны
   в `effectivePrice` и `effectiveDurationMin`.
2. `GET /api/v1/veterinarians` и `GET /api/v1/veterinarians/{id}/species` — выбрать врача, который лечит этот вид
   и имеет специализацию выбранных услуг.
3. `GET /api/v1/work-schedules?veterinarianId=...` и `GET /api/v1/schedule-exceptions?veterinarianId=...` — посмотреть
   расписание врача.
4. `GET /api/v1/appointments/slots?speciesId=...&serviceIds=...&serviceIds=...&from=...&to=...` — найти свободные слоты за период
   (даты клиники `from`–`to` включительно, не больше 14 дней). Каждый слот — `{startAt, endAt, veterinarianIds}`:
   какие врачи свободны в это время. С параметром `veterinarianId` ищутся слоты только этого врача. Длина слота равна
   сумме длительностей услуг для вида плюс максимальный буфер среди услуг. Допускается также один параметр
   `serviceIds` с UUID через запятую. Слот можно сразу передать в запись. Вместо поиска можно
   проверить конкретный слот через `GET /api/v1/appointments/availability`. Проверка возвращает `404`
   для неизвестного врача, `422` для неактивного врача или времени вне его расписания, `409` для занятого слота.
5. `POST /api/v1/client/appointments` — записаться, передав `serviceIds` массивом. Запись создаётся в статусе
   `PENDING`, цену считает сервер. `startAt` должен быть в будущем. Сервер проверяет, что `endAt` равен началу
   плюс сумма длительностей услуг для вида животного (либо базовых длительностей) и максимальный буфер;
   несовпадение возвращает `422` с ошибкой поля `endAt`. Все запланированные услуги должны быть активны, доступны
   виду питомца и относиться к одной специализации из списка врача. Несовместимые услуги дают `422`.
6. Врач подтверждает и завершает приём через `PATCH /api/v1/veterinarian/appointments/{id}`.
   При завершении обязательны `status: "COMPLETED"` и полный массив `performedServiceIds` фактически оказанных услуг.
7. При необходимости врач назначает повторный приём через `POST /api/v1/veterinarian/appointments/{id}/follow-ups`
   (тело: `startAt`, `endAt` и обязательный массив `serviceIds`). Услуги исходного приёма автоматически не копируются. Повторный приём
   создаётся к этому же врачу для того же питомца сразу в статусе `CONFIRMED`, ссылается на исходный через
   `followUpOf`, цену считает сервер. Исходный приём должен быть в статусе `CONFIRMED` или `COMPLETED`, а повторный —
   начинаться после его окончания.

## Несколько услуг в одной записи

Это изменение контракта: в создании записи, поиске слотов и назначении повторного приёма `serviceId` заменён
на `serviceIds`. В `AppointmentResponse` вместо единственных `serviceId` и `priceSnapshot` возвращаются
`services`, `estimatedTotal`, `actualTotal`, `durationMin` и `bufferAfterMin`. Старые клиенты необходимо обновить
одновременно с бэкендом; отдельная «первая услуга» для совместимости не возвращается. Фильтр администратора
`serviceId` остаётся одиночным и выбирает записи, содержащие соответствующую позицию, без дублей записей.

Одна запись относится к одному питомцу и одному врачу. Для нового плана требуется от 1 до 20 различных услуг;
повторяющиеся UUID отклоняются, количество единиц одной услуги в этой версии не поддерживается.
У каждой услуги длительность и цена берутся из `service_species`, если переопределение задано, иначе из `service`.

```text
durationMin = сумма длительностей запланированных услуг
bufferAfterMin = максимальный bufferAfterMin запланированных услуг
endAt = startAt + durationMin + bufferAfterMin
```

Например, услуги длительностью 30 и 20 минут с буферами 10 и 15 минут занимают 65 минут, включая один буфер.
При начале в 10:00 услуги заканчиваются в 10:50, занятость — в 11:05. При шаге сетки 15 минут следующий
приём может начаться в 11:15. Длительность не округляется; сетка ограничивает время начала.
Весь интервал должен непрерывно помещаться в график врача, не пересекать обед, отсутствие и другие записи.
Проверка выполняется и при поиске, и при сохранении. Пересекающиеся интервалы у одного врача дополнительно
защищены ограничением БД. Занятый слот возвращает `409` с `error.name = "AppointmentSlotConflictException"`
и при проверке расписания, и при конфликте одновременных сохранений.

Каждая позиция `services` содержит:

| Поле | Значение |
|---|---|
| `serviceId` | ID услуги в каталоге |
| `nameSnapshot`, `priceSnapshot` | Название и цена, зафиксированные при добавлении позиции |
| `durationMinSnapshot`, `bufferAfterMinSnapshot` | Зафиксированная длительность процедуры и её буфер |
| `isPlanned` | Услуга входит в забронированный план |
| `isPerformed` | `null` — выполнение ещё не подтверждено, `true` — оказана, `false` — не оказана или отметка исправлена |
| `addedBy`, `createdAt` | Автор и время добавления |
| `updatedBy`, `updatedAt` | Автор и время последнего изменения позиции |

`estimatedTotal` — сумма цен запланированных позиций. `actualTotal` до завершения равен `null`, после
`COMPLETED` — сумме цен фактически оказанных позиций, включая дополнительные. Это стоимость услуг,
а не сведения об оплате. Изменение каталога не переоценивает сохранённые позиции. Новые позиции получают
цену, действующую при добавлении. Услуги в ответах загружаются пакетно, без отдельного SQL-запроса на каждую позицию.

Администратор изменяет любую запись через `PATCH /api/v1/admin/appointments/{id}`, врач — назначенную ему
через `PATCH /api/v1/veterinarian/appointments/{id}`. Для клиента изменение плана и оказанных услуг недоступно.
Оба эндпоинта принимают:

| Поле | Поведение |
|---|---|
| `serviceIds` | Заменяет весь план до начала приёма в статусе `PENDING` или `CONFIRMED`; занятость пересчитывается и проверяется |
| `performedServiceIds` | Полный набор фактически оказанных услуг, включая новые ID; допускается пустой массив, максимум 20 разных ID |
| `endAt` | Явное изменение занятого интервала с проверкой доступности; врач может только продлевать его |

В плане все услуги относятся к одной специализации. В `performedServiceIds` можно указать услуги из
нескольких специализаций врача в одном запросе. Сервер сверяет весь переданный набор с текущими назначениями
врача. Новые позиции должны быть активны и доступны для вида питомца.

Оказанные услуги можно записывать после начала приёма в статусе `CONFIRMED` и после `COMPLETED`.
Для `CANCELLED` и `NO_SHOW` это запрещено. При переходе в `COMPLETED` обязателен `performedServiceIds`:
план не считается выполненным автоматически. Услуги, отсутствующие в переданном фактическом наборе,
получают `isPerformed: false`; оказанные позиции не удаляются физически при исправлении. Повторная передача
одного и того же набора не создаёт дубли. Изменения сохраняют автора и время.

Если уже есть оказанные услуги, отмена записи и отметка неявки запрещены: сначала нужно явно исправить
фактический набор услуг. Повторная отмена сохраняет первоначальные автора, время и причину.

Например, завершение диагностики с дополнительно выполненной вакцинацией:

```json
{
  "status": "COMPLETED",
  "performedServiceIds": ["11111111-1111-1111-1111-111111111111", "22222222-2222-2222-2222-222222222222"]
}
```

Добавление вакцинации после завершения выполняется тем же `performedServiceIds` без изменения статуса,
с сохранением уже оказанной диагностики в массиве. При этом фактическая стоимость меняется, а `startAt` и `endAt`
сохраняются. Если во время приёма нужно занять больше времени врача, необходимо отдельно передать `endAt`;
система проверит график и пересечения. Следующие записи автоматически не сдвигаются. Позиция услуги
«Вакцинация» не создаёт медицинскую запись `Vaccination`: для неё используется существующее API прививок.

Миграция `V11` переносит старую услугу в одну позицию и сохраняет исходные цену, интервал и статус.
Для старых завершённых записей услуга считается оказанной. Исторические длительность и буфер достоверно
неизвестны, поэтому их снимки и итоговые `durationMin`/`bufferAfterMin` равны `null`; старые интервалы не пересчитываются.
Перед применением ограничения пересечений нужно устранить существующие пересекающиеся неотменённые записи:
миграция не удаляет и не переносит их автоматически. `V12` добавляет тип уведомления об изменении услуг.
Для `V11` требуется расширение PostgreSQL `btree_gist`: оно должно быть установлено заранее либо у пользователя
миграции должны быть права на его установку.

Все обновления — `PATCH`: поля, отсутствующие в теле запроса, не меняются; явный `null` очищает nullable-поле.

Статусы записи: `PENDING → CONFIRMED | CANCELLED`, `CONFIRMED → COMPLETED | CANCELLED | NO_SHOW`.
`COMPLETED`, `CANCELLED` и `NO_SHOW` — конечные.

Клиент отменяет свою запись через `POST /api/v1/client/appointments/{id}/cancel`.
Тело необязательно: можно передать `{"reason":"Не смогу прийти"}` (не более 1000 символов).
Врач отменяет свою запись через `PATCH /api/v1/veterinarian/appointments/{id}` с
`{"status":"CANCELLED","cancelReason":"Причина отмены"}`; администратор — через
`PATCH /api/v1/admin/appointments/{id}` с теми же полями.
В `AppointmentResponse` доступны `cancelledBy`, `cancelledAt` и `cancelReason`.
При переходе в `CANCELLED` сервер сам записывает текущего пользователя и время отмены.
Физическое удаление через `DELETE /api/v1/admin/appointments/{id}` разрешено только для `CANCELLED`;
остальные статусы возвращают `422`. Уведомления сохраняются после удаления, их `appointmentId` становится `null`.
Ограничения состояния приёма, например перенос завершённого визита или отмена после оказания услуги, дают `422`.
Отсутствующий массив `performedServiceIds` при завершении даёт `400`.

Моменты времени (`startAt`, `endAt`, `createdAt` и т. п.) передаются как ISO-8601 Instant,
например `2026-11-08T09:00:00Z`. Даты без времени (`from` / `to` поиска слотов, даты рождения,
прививок и ревакцинации) — `YYYY-MM-DD`. Часовой пояс клиники по умолчанию — `Europe/Moscow`,
шаг начала слота — 15 минут (`clinic.zone`, `clinic.slot-step-min`).

У одного врача интервалы дат `CUSTOM_HOURS` не должны пересекаться, включая граничные даты:
создание или изменение с пересечением возвращает `409`. Если конфликт уже есть в сохранённых данных,
проверка доступности сообщает о нём, а поиск не предлагает слоты на такие даты до исправления исключений.

Проверки дат рождения и вакцинации используют текущую дату в часовом поясе клиники (`clinic.zone`),
в том числе при проверке `@PastOrPresent` во входящих запросах.

## Статистика (администратор)

Все эндпоинты — `GET /api/v1/admin/statistics/...` (группа `Admin: Statistics`) — принимают необязательные `from`
и `to`: даты клиники (ISO-8601, `2026-10-01`), обе включительно. Без дат берётся текущий месяц; если указана только
одна дата, вторая берётся из её месяца (`from=2026-11-15` → по `2026-11-30`). `from` не может быть позже `to`.
Запись попадает в период по времени начала приёма (`startAt`).

Выручка (`revenue`) — сумма цен фактически оказанных услуг записей в статусе `COMPLETED`; ожидаемая выручка
(`expectedRevenue`) — сумма цен запланированных услуг в `PENDING` и `CONFIRMED`. Дополнительные услуги,
внесённые после завершения, корректируют выручку в периоде исходного приёма. Один приём с несколькими
услугами считается одним приёмом в общих показателях, по врачам и видам. В разбивке по услугам каждая
позиция относится к своей услуге, а выручка считается по цене этой позиции, без повторения общей суммы приёма.

| Эндпоинт | Что возвращает |
|---|---|
| `/overview` | Сводка: `totalAppointments`, `appointmentsByStatus` (все статусы, включая нулевые), `revenue`, `expectedRevenue`, `averageCheck` (выручка / число завершённых), `cancellationRate` (`CANCELLED` / все), `noShowRate` (`NO_SHOW` / (`COMPLETED` + `NO_SHOW`)), `followUps` (повторные приёмы), `newClients`, `newPets` (созданы за период). Доли — от 0 до 1; `averageCheck` и доли равны `null`, если делить не на что |
| `/timeline?granularity=DAY\|WEEK\|MONTH` | Точки `{periodStart, appointments, completed, revenue}` по дням (по умолчанию), неделям (с понедельника) или месяцам, включая пустые. Считаются только записи внутри периода, поэтому первая и последняя неделя или месяц могут быть неполными |
| `/veterinarians` | По врачам, у которых есть записи за период: `{veterinarianId, fullName, appointments, completed, cancelled, noShows, revenue}` |
| `/services` | По услугам, у которых есть записи за период: `{serviceId, name, specializationName, appointments, completed, revenue}` |
| `/species` | По всем видам: `{speciesId, name, activePets, appointments, revenue}`; `activePets` — текущее число неархивных питомцев, от периода не зависит |

Списки отсортированы по выручке по убыванию, затем по имени.

## Уведомления

Уведомления хранятся на сервере; каждый пользователь видит только свои. Тексты `title` и `body` системных уведомлений формируются на русском
в момент события (время — в часовом поясе клиники) и потом не меняются, даже если запись изменилась.

| Тип | Когда | Кому |
|---|---|---|
| `APPOINTMENT_BOOKED` | создана обычная запись в статусе `PENDING` | врачу; при записи клиентом — также всем администраторам; при создании администратором — также владельцу |
| `APPOINTMENT_CONFIRMED` | запись подтверждена | владельцу |
| `APPOINTMENT_CANCELLED` | запись отменена | клиентом — врачу и всем администраторам; врачом — владельцу; администратором — владельцу и врачу |
| `APPOINTMENT_RESCHEDULED` | администратор изменил время или врача | владельцу и врачу; при смене врача — и прежнему врачу |
| `APPOINTMENT_NO_SHOW` | отмечена неявка | владельцу |
| `APPOINTMENT_COMPLETED` | приём завершён | владельцу |
| `APPOINTMENT_NOTES_UPDATED` | заметки добавлены, изменены или очищены | `vetNotes` — владельцу; `clientComment` — врачу |
| `APPOINTMENT_SERVICES_UPDATED` | изменён план или фактический набор услуг; при завершении сведения входят в уведомление `APPOINTMENT_COMPLETED` | владельцу и врачу, кроме автора изменения |
| `FOLLOW_UP_SCHEDULED` | назначен повторный приём в статусе `PENDING` или `CONFIRMED` | владельцу; при создании администратором — также врачу; статус указан в тексте |
| `SCHEDULE_CONFLICT` | изменение графика или отключение врача создало конфликт с будущим приёмом | всем администраторам, включая автора изменения |
| `APPOINTMENT_REMINDER` | в пределах 24 часов до приёма в статусе `PENDING` или `CONFIRMED` (проверка каждые 5 минут) | владельцу, один раз на каждое время начала записи |
| `VACCINATION_DUE` | в пределах 7 дней до даты ревакцинации (проверка ежедневно в 09:00) | владельцу неархивного питомца, один раз на каждый срок прививки; не приходит, если питомцу уже сделали более позднюю прививку с тем же названием |
| `VACCINATION_OVERDUE` | дата ревакцинации раньше сегодняшнего дня клиники | владельцу неархивного питомца, один раз на каждый срок; более поздняя прививка с тем же названием отменяет необходимость напоминания |
| `VACCINATION_CREATED` | врач или администратор добавил прививку | владельцу питомца |
| `VACCINATION_UPDATED` | изменены название, дата введения или следующий срок, включая его очистку | владельцу питомца |
| `VACCINATION_DELETED` | администратор удалил прививку | владельцу; уведомление сохраняет текст после удаления |
| `ACCOUNT_UPDATED` | изменены ФИО, email или телефон | владельцу аккаунта, в том числе при собственном изменении |
| `PASSWORD_CHANGED` | успешно изменён пароль | владельцу аккаунта, включая автора действия |
| `PET_UPDATED` | администратор изменил данные карточки питомца | владельцу питомца |
| `PET_ARCHIVED` / `PET_RESTORED` | питомец архивирован или восстановлен | владельцу, в том числе при собственном действии |
| `ADMIN_MESSAGE` | администратор отправил сообщение | выбранному пользователю |

Уведомления участникам приёма исключают автора действия. При создании записи сразу в `CONFIRMED`, `CANCELLED`,
`COMPLETED` или `NO_SHOW` обе стороны получают уведомление соответствующего статуса вместо сообщения о новой записи;
для повторных приёмов в `CONFIRMED` сохраняется `FOLLOW_UP_SCHEDULED`.
Повторное сохранение прежнего статуса и неизменившихся заметок уведомлений не создаёт. Одновременное изменение статуса
и заметок создаёт отдельное уведомление о каждом событии. Сами заметки в уведомление не копируются.

После изменения `startAt` или `nextDueOn` напоминание о новом сроке снова доступно; каждая проверка планировщика
не дублирует уже отправленное напоминание о том же сроке. Сроки напоминаний и расписание проверок настраиваются
в `application.yaml` (`notification.*`).

Проверка ревакцинации в 09:00 обрабатывает и предстоящие, и уже просроченные сроки. Отправленное ранее
`VACCINATION_DUE` не блокирует отдельное уведомление о наступившей просрочке; ежедневные повторы
`VACCINATION_OVERDUE` подавляются. После простоя сервера всё ещё актуальные просроченные прививки попадут
в следующий запуск. При первом запуске новой версии могут прийти сообщения об уже накопившихся просрочках.

Изменения аккаунта сравниваются с сохранёнными значениями: повторное сохранение тех же данных уведомления
не создаёт. Текст содержит только названия изменённых полей, без значений email, телефона, паролей или хешей.
Для карточки питомца учитываются имя, вид, пол, дата рождения, вес, порода, заметки и архивный статус;
изменение фото и обычное редактирование владельцем собственной карточки уведомлений не создают.
Полные заметки в тексты уведомлений не копируются.

Кандидаты на ревакцинацию выбираются вместе с владельцами и именами питомцев одним запросом с JOIN;
архивные питомцы, заменённые более поздней прививкой записи и уже отправленные события исключаются в SQL.
Новые массовые уведомления записываются пакетами до 1000 строк с `RETURNING`; публикация в WebSocket происходит
после фиксации транзакции только для вставленных строк. Для клиентских записей и отмен список администраторов
загружается одной выборкой; контекст приёма повторно для каждого администратора не загружается.

При создании, изменении и удалении рабочих графиков и исключений, а также при отключении врача проверяются
его будущие записи `PENDING` и `CONFIRMED`. Для каждой новой конфликтующей записи создаётся `SCHEDULE_CONFLICT`
с привязкой к приёму. Уже существующие конфликты повторно не рассылаются при следующем редактировании.
Автоматической отмены или переноса нет: администратор связывается с клиентом и после согласования выполняет
`PATCH /api/v1/admin/appointments/{id}` — либо `status=CANCELLED` с причиной, либо новые `startAt` / `endAt`
и при необходимости `veterinarianId`. Перенос проверяет доступность нового слота; отмена и перенос уведомляют участников.

REST (группа `Notifications`):

- `GET /api/v1/notifications?unreadOnly=&page=&size=` — постранично, новые сверху. Элемент: `{id, type, title, body,
  actorId, appointmentId, petId, vaccinationId, readAt, createdAt}`; `actorId` — кто совершил действие (`null` для
  напоминаний), `readAt = null` — не прочитано.
- `GET /api/v1/notifications/unread-count` — число непрочитанных.
- `POST /api/v1/notifications/{id}/read` — отметить прочитанным (уже прочитанное сохраняет `readAt`; чужое — `404`).
- `POST /api/v1/notifications/read-all` — отметить все; в `result` — сколько было непрочитанных.

Персональные сообщения администратора (группа `Admin: Notifications`, требуется роль `ADMIN`):

- `POST /api/v1/admin/notifications/users/{recipientId}` — отправить одному пользователю; неизвестный получатель — `404`.

Тело запроса:

```json
{
  "title": "Изменение расписания",
  "body": "Пожалуйста, уточните время приёма у администратора.",
  "appointmentId": null,
  "petId": null,
  "vaccinationId": null
}
```

`title` и `body` обязательны, не могут быть пустыми или состоять из пробелов; максимум 200 и 4000 символов соответственно.
Все три ID необязательны и могут отсутствовать или быть `null`. Переданные объекты должны существовать (`404`) и,
если указано несколько привязок, относиться к одному питомцу (`422` при несовпадении). Привязка не даёт получателю
дополнительных прав на просмотр объекта. При удалении отменённого приёма сообщение сохраняется с `appointmentId=null`;
при удалении прививки сообщение также сохраняется с `vaccinationId=null`.
При удалении питомца действует прежнее каскадное удаление связанных уведомлений.

Ответ — `201 Created`, в `ApiResponse.result` — созданное уведомление в формате `NotificationResponse`
(`id`, `type`, `title`, `body`, `actorId`, `appointmentId`, `petId`, `vaccinationId`, `readAt`, `createdAt`).
Сохраняется непрочитанное уведомление
с типом `ADMIN_MESSAGE`, произвольными текстами и `actorId` текущего администратора. Прочитанность по-прежнему задаётся
через `readAt`. Уведомление передаётся в существующие каналы доставки только после фиксации транзакции.

Новые уведомления сразу приходят по WebSocket, протокол STOMP 1.2 (например, `@stomp/stompjs`):

1. Подключиться к `ws://localhost:8080/ws` (в демо — `ws://localhost:8081/ws`, через HTTPS — `wss://<host>/ws`;
   нативный WebSocket, без SockJS). Браузер не может передать токен при открытии
   соединения, поэтому он передаётся в кадре `CONNECT`: заголовок `Authorization: Bearer <accessToken>`.
2. Подписаться на `/user/queue/notifications`. Каждое сообщение — JSON того же вида, что элемент списка в REST.

Сервер публикует уведомления в `/user/queue/notifications`. Подписки разрешены только внутри `/user/queue/`;
подписка вне этого префикса и отправка `SEND` отклоняются кадром `ERROR`, как и
`CONNECT` без действительного токена; после `ERROR` соединение закрывается. Токен проверяется при подключении, поэтому
открытое соединение продолжает работать и после истечения токена. Пока соединения нет, уведомления не теряются: после
подключения фронтенд берёт пропущенное из `GET /api/v1/notifications` и `unread-count`.

WebSocket использует те же разрешённые origin, что и HTTP API (`cors.allowed-origins`).

## Формат ответа

Ответы прикладного REST API с телом обёрнуты в `ApiResponse`:

```json
{
  "success": true,
  "result": { },
  "error": null,
  "timestamp": "2026-09-15T10:00:00Z"
}
```

Health check, OpenAPI и STOMP-сообщения используют собственные форматы.

При ошибке `success = false`, `result = null`, а в `error` лежат имя исключения, сообщение, HTTP-статус, путь запроса
и, для ошибок валидации, список нарушений по полям (`violations`).

Постраничные списки — `GET /api/v1/admin/{appointments,users,pets,vaccinations,schedule-exceptions}`,
`GET /api/v1/client/appointments`, `GET /api/v1/veterinarian/{appointments,pets,vaccinations}`
и `GET /api/v1/notifications` — принимают `page`
(с 0, по умолчанию 0) и `size` (1–100, по умолчанию 20), а в `result` возвращают страницу:

```json
{
  "items": [ ],
  "page": 0,
  "size": 20,
  "totalElements": 41,
  "totalPages": 3
}
```

`totalElements` — сколько записей подходит под фильтр всего, а не на текущей странице. Фильтры необязательны
и объединяются через AND; несколько статусов передаются повтором параметра: `?status=PENDING&status=CONFIRMED`.
Текстовые фильтры (`search`, `name`) ищут подстроку без учёта регистра. Публичные `GET /api/v1/services`
и `GET /api/v1/veterinarians` отдают только активные записи; все записи, включая неактивные, — в
`GET /api/v1/admin/services` и `GET /api/v1/admin/veterinarians`.

| Статус | Когда |
|---|---|
| `200` / `201` / `204` | Успех; `201` — при создании, `204` — при удалении или смене пароля (без тела) |
| `400` | Ошибка валидации или некорректный запрос |
| `401` | Нет токена, токен недействителен или истёк, неверные данные при входе. На защищённых маршрутах передаётся `WWW-Authenticate: Bearer` |
| `403` | Недостаточно прав или чужой ресурс |
| `404` | Сущность не найдена |
| `405` | HTTP-метод не поддерживается. Заголовок `Allow` перечисляет поддерживаемые методы |
| `409` | Занятый слот, пересечение исключений расписания, дубликат или конфликт при удалении связанной записи |
| `422` | Нарушено бизнес-правило, например питомец в архиве или врач не лечит этот вид |
| `503` | База данных недоступна |

## Фотографии

Фотографии поддерживаются у ветеринаров и питомцев. У пользователя фото нет.
Внутренний `photoKey` не передаётся клиенту и не принимается в запросах.
Обычные create/update запросы ветеринара больше не принимают `photoUrl`;
сначала создайте профиль, затем загрузите фотографию отдельным запросом.

| Ресурс | PUT (загрузить/заменить) и DELETE (удалить) | Доступ |
|---|---|---|
| Свой профиль врача | `/api/v1/veterinarian/profile/photo` | Текущий ветеринар |
| Врач | `/api/v1/admin/veterinarians/{id}/photo` | Администратор |
| Свой питомец | `/api/v1/client/pets/{id}/photo` | Владелец |
| Питомец | `/api/v1/admin/pets/{id}/photo` | Администратор |

PUT: `Authorization: Bearer <JWT>`, `multipart/form-data`, часть `file`.
Поддерживаются JPEG и PNG до 5 МБ и 20 млн пикселей. MIME-заголовок не заменяет проверку содержимого.
Результат — центральный квадрат JPEG 64×64 и 512×512. Исходник не хранится.

Ответ PUT — HTTP 200, обычный `ApiResponse`, в `result`:

```json
{
  "photoUrl": "http://localhost:3905/chiron-media/pets/.../512.jpg?X-Amz-...",
  "photoThumbnailUrl": "http://localhost:3905/chiron-media/pets/.../64.jpg?X-Amz-...",
  "photoUrlExpiresAt": "2026-11-11T12:15:00Z"
}
```

Те же поля входят в обычные ответы списков и карточек ветеринаров/питомцев.
При отсутствии фото все три поля равны `null`. DELETE возвращает 204, в том числе при повторном удалении.
Клиентам доступны только свои питомцы, ветеринарам — их пациенты, администраторам — все.
Фото врачей доступны через публичный каталог. Бакет закрыт; подписанные GET-ссылки действуют 15 минут.
Для обновления ссылки повторите GET ресурса. JWT Chiron к запросу изображения прикладывать не нужно.
Полученные ссылки нельзя хранить как постоянные идентификаторы или передавать посторонним.

Ошибки: 400 — некорректный файл, формат multipart или отсутствующая часть; 413 — превышен размер загрузки;
401 — нет авторизации; 403 — нет доступа; 404 — нет сущности; 503 — недоступно хранилище.
Старое фото остаётся действующим, если загрузка одной из версий либо фиксация в БД не удалась.
Физическое удаление старых объектов происходит асинхронно, обычно в течение минуты; при сбое повторяется.
