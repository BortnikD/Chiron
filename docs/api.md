# Документация API Chiron

Документация API генерируется автоматически из кода бэкенда (springdoc-openapi). Отдельно её поддерживать не нужно:
описания эндпоинтов берутся из аннотаций `@Operation` и `@Tag` в контроллерах.

## Как открыть

Сначала запустите бэкенд (`chiron`) с профилем `local`. По умолчанию он слушает порт `8080`.

| Вариант | Адрес | Когда использовать |
|---|---|---|
| **Scalar** | http://localhost:8080/scalar.html | Основной вариант: удобный поиск, примеры запросов на разных языках, отправка запросов из браузера. Загружается с CDN, нужен интернет |
| **Swagger UI** | http://localhost:8080/swagger-ui.html | Классический интерфейс; работает без интернета |
| **OpenAPI JSON** | http://localhost:8080/v3/api-docs | Сырая спецификация: импорт в Postman / Insomnia / Bruno, генерация клиента для фронтенда |
| **Use case диаграмма** | [`docs/usecase.excalidraw`](./usecase.excalidraw) | Открыть на https://excalidraw.com (Open → выбрать файл) или в VS Code с расширением Excalidraw |

Документация (`/scalar.html`, `/swagger-ui.html`, `/v3/api-docs`, `/v3/api-docs.yaml`) доступна без авторизации только в `local`.
В `production` и без активного профиля доступ запрещён, в том числе авторизованным пользователям.

## Проверка состояния (health check)

Эндпоинты Spring Boot Actuator. Доступны **без токена**, только `GET`. В документации они в группе `Actuator`.

| Эндпоинт | Что проверяет | Когда использовать |
|---|---|---|
| `GET /actuator/health` | Приложение и подключение к базе данных | Общая проверка «бэкенд работает»: индикатор на фронтенде, мониторинг |
| `GET /actuator/health/readiness` | Приложение запущено и база данных доступна | Можно ли уже отправлять запросы (используется в healthcheck Docker Compose) |
| `GET /actuator/health/liveness` | Процесс приложения жив (базу **не** проверяет) | Нужно ли перезапускать контейнер |

Ответ **не** обёрнут в `ApiResponse`. Подробности о компонентах (версия БД, место на диске и т. п.) не
отдаются, только итоговый статус:

```json
{ "status": "UP" }
```

| HTTP-статус | `status` | Значение |
|---|---|---|
| `200` | `UP` | Всё работает |
| `503` | `DOWN` / `OUT_OF_SERVICE` | Бэкенд запущен, но не готов, например недоступна база данных |
| нет ответа / сетевая ошибка | — | Бэкенд не запущен или недоступен по сети |

Пример проверки на фронтенде:

```ts
export async function isBackendHealthy(): Promise<boolean> {
  try {
    const response = await fetch("http://localhost:8080/actuator/health", {
      signal: AbortSignal.timeout(3000),
    });
    // 503 comes with a JSON body too, so checking response.ok is enough.
    return response.ok;
  } catch {
    // Network error or timeout: the backend is not reachable.
    return false;
  }
}
```

CORS для этих эндпоинтов настроен так же, как для остального API (origin'ы из `cors.allowed-origins`).

## Авторизация

API использует JWT-токен. Токен один и живёт 30 дней, refresh-токена нет.

1. Получите токен:
   - `POST /api/v1/auth/register` — регистрация, всегда создаёт пользователя с ролью `CLIENT`;
   - `POST /api/v1/auth/login` — вход по email и паролю.
2. Возьмите `result.accessToken` из ответа.
3. Передавайте его в заголовке `Authorization: Bearer <token>`.
   - В Scalar: блок **Authentication** → `bearerAuth` → вставить токен.
   - В Swagger UI: кнопка **Authorize** → вставить токен (без слова `Bearer`).
4. `GET /api/v1/users/me` — проверить, под кем вы авторизованы; `PATCH /api/v1/users/me` — изменить свои данные
   (имя, отчество, фамилию, email, телефон). `fullName` сервер собирает сам в формате `И. О. Фамилия`.

Первый администратор создаётся при старте приложения из переменных `ADMIN_*` в файле `chiron/.env`
(шаблон — `chiron/.env.example`). Ветеринаров и других администраторов создаёт администратор через
`POST /api/v1/admin/users`.

## Что куда

Эндпоинты разделены по ролям. Раздел в документации соответствует префиксу URL, а группы (теги) подписаны
префиксом роли.

| Префикс | Доступ | Группы в документации | Что внутри |
|---|---|---|---|
| `/api/v1/auth` | всем | `Auth` | Регистрация и вход |
| `/api/v1/users/me` | любая роль, с токеном | `Users` | Просмотр и изменение своих данных |
| `/api/v1/notifications`, `/ws` | любая роль, с токеном | `Notifications` | Свои уведомления: список, счётчик непрочитанных, отметка о прочтении; получение новых в реальном времени по STOMP |
| `/api/v1/...` (GET) | всем, без токена | `Species`, `Specializations`, `Services`, `Service species`, `Veterinarians`, `Veterinarian species permissions`, `Work schedules`, `Schedule exceptions`, `Appointments` | Справочники клиники: виды животных, специализации, услуги и их цены по видам, врачи и какие виды они лечат, расписание врачей, поиск свободных слотов и проверка слота |
| `/api/v1/client/...` | `CLIENT` | `Client: Pets`, `Client: Appointments`, `Client: Vaccinations` | Свои питомцы; запись на приём, список и отмена своих записей; прививки своих питомцев |
| `/api/v1/veterinarian/...` | `VETERINARIAN` | `Veterinarian: Profile`, `Veterinarian: Appointments`, `Veterinarian: Pets`, `Veterinarian: Vaccinations` | Свой профиль врача (просмотр, изменение описания, фото и стажа); свои записи — смена статуса, заметки врача и назначение повторного приёма; пациенты (питомцы, у которых была запись к этому врачу) и их прививки |
| `/api/v1/admin/...` | `ADMIN` | `Admin: *` | Полное управление: пользователи, питомцы, записи, прививки, врачи и их допуски к видам, расписания и исключения из расписания, справочники; статистика клиники |

Клиент и ветеринар видят только свои данные. Попытка обратиться к чужому ресурсу возвращает `403`.
Администратор работает с данными любых пользователей.

## Смена пароля

`POST /api/v1/users/me/password` доступен всем авторизованным ролям с Bearer-токеном:

```json
{ "currentPassword": "old-password", "newPassword": "new-password" }
```

Ограничения нового пароля совпадают с регистрацией: минимум 8 символов и максимум 72 байта UTF-8.
Сервер проверяет текущий пароль и сохраняет BCrypt-хеш нового. При успехе возвращается `204` без тела;
при невалидных данных — `400`, при неверном текущем пароле — `401`.
Ранее выданные JWT остаются действительными до истечения срока: смена пароля их не отзывает.

## ФИО врача

`VeterinarianResponse` содержит `firstName`, `middleName` (может быть `null`), `lastName` и `fullName`.
Поля читаются из связанного пользователя, поэтому изменение его имени отражается в последующих ответах о враче.
`fullName` сохраняет общий формат отображения `I. M. Lastname`; для полного ФИО доступны отдельные части имени.
Эти поля возвращаются в публичном каталоге и деталях врача, админских ответах и собственном профиле ветеринара,
включая ответы создания и обновления. `userId` и остальные поля сохранены.

## Виды животных у врача

`VeterinarianResponse` содержит `speciesIds` — массив ID видов, которых разрешено лечить врачу.
Без назначенных разрешений возвращается `[]`. Поле доступно в публичном каталоге, деталях врача,
админских ответах и собственном профиле ветеринара. У только что созданного профиля массив пустой;
создание и удаление разрешений отражаются в последующих чтениях.

Список врачей загружает разрешения пакетно, без отдельного запроса на каждого врача.
Фильтр `speciesId` по-прежнему отбирает врачей, но `speciesIds` каждого найденного врача содержит все его виды.

## Цена и длительность услуги для вида животного

`GET /api/v1/services?speciesId=<UUID>` возвращает доступные для вида активные услуги с полями
`effectivePrice` и `effectiveDurationMin`. Каждое поле независимо использует переопределение для вида,
а если оно не задано (`null`) — соответствующее базовое значение. `basePrice` и `baseDurationMin` сохраняются.
`effectiveDurationMin` не включает `bufferAfterMin`.

Без `speciesId` расчётные поля равны `null`. Они также равны `null` в ответах отдельных услуг и админских
операций, где расчёт для вида не запрашивается. Для списка с видом сервер пакетно загружает переопределения,
без отдельного запроса на каждую услугу.

## Прививки питомцев клиента

`GET /api/v1/client/vaccinations` возвращает массив прививок всех питомцев текущего клиента.
Необязательный `petId` ограничивает выборку одним своим питомцем; для чужого питомца возвращается `403`.
Ограничение по владельцу применяется в запросе к БД и при отсутствии `petId`.

Необязательные `nextDueFrom` и `nextDueTo` задают включительные границы `nextDueOn` в формате `YYYY-MM-DD`.
Если указана хотя бы одна граница, прививки без даты ревакцинации не возвращаются.
Обратный диапазон (`nextDueFrom > nextDueTo`) возвращает `400`.

Сортировка: `nextDueOn` по возрастанию, записи без даты — в конце, при равной дате — по `id` по возрастанию.
Ответ остаётся массивом без пагинации. Например, `?nextDueTo=2026-11-08` вернёт все прививки с истёкшим
или наступающим до этой даты сроком, включая саму дату.

## Сортировка записей клиента

`GET /api/v1/client/appointments` принимает необязательный `direction=ASC|DESC`.
По умолчанию сохраняется `ASC`; для истории с новыми записями сверху используйте `direction=DESC`.
Сортировка выполняется в БД по `startAt`, затем по `id` в том же направлении, до применения пагинации.
Фильтры `petId`, `status`, `from`, `to` и ограничение по текущему владельцу сохраняются.

Пример: `GET /api/v1/client/appointments?status=COMPLETED&direction=DESC&page=0&size=20`.

## Сводка питомца по запросу

`GET /api/v1/client/pets` и `GET /api/v1/client/pets/{id}` принимают `withSummary`, по умолчанию `false`.
Без флага или с `withSummary=false` формат JSON сохраняется: `summary` отсутствует, дополнительные запросы
к записям и прививкам не выполняются. При `withSummary=true` добавляется объект `summary`:

| Поле | Значение |
|---|---|
| `completedVisits` | Количество записей со статусом `COMPLETED` |
| `appointmentsCount` | Количество всех записей, включая отменённые |
| `vaccinationsCount` | Количество всех записей о прививках |
| `nextAppointment` | Ближайшая запись `PENDING` или `CONFIRMED` с `startAt >= now`: `{id, startAt, serviceId}`; иначе `null` |
| `nextVaccinationDueOn` | Минимальный актуальный срок ревакцинации, включая просроченные; иначе `null` |
| `hasOverdueVaccination` | Актуальный срок ревакцинации строго раньше сегодняшней даты в часовом поясе клиники |

Более новая прививка с тем же названием без учёта регистра делает срок предыдущей неактуальным.
Если несколько прививок сделаны в один день, их сроки учитываются наравне; это совпадает с правилом уведомлений.
Отсутствие дат ревакцинации даёт `nextVaccinationDueOn=null` и `hasOverdueVaccination=false`, но не подтверждает
полноту вакцинации. Отсутствующие счётчики равны нулю. Для одинакового времени приёма выбирается запись с меньшим `id`.

Сводки рассчитываются пакетно только для выбранных питомцев текущего владельца; `isArchived` продолжает работать.
Используется четыре дополнительных SQL-запроса независимо от количества питомцев; полная история в память
не загружается. Для пустого списка дополнительные запросы не выполняются. Создание и обновление питомцев,
а также API администратора и ветеринара сохраняют прежние ответы.

## Сводка кабинета клиента

`GET /api/v1/client/summary` возвращает показатели текущего клиента в `ApiResponse`:

| Поле | Значение |
|---|---|
| `activePets` | Количество неархивных питомцев |
| `upcomingAppointments` | Количество записей `PENDING` и `CONFIRMED` с `startAt >= now` |
| `completedAppointments` | Количество всех записей `COMPLETED` |
| `vaccinationsDue` | Количество актуальных записей о прививках со сроком до `today + leadDays` включительно, включая просроченные |
| `vaccinationsOverdue` | Из них — количество со сроком строго раньше `today` |
| `unreadNotifications` | Количество непрочитанных уведомлений |
| `nextAppointment` | Ближайшая предстоящая запись в формате `AppointmentResponse`, либо `null` |

Приёмы учитываются и для архивных питомцев: архивирование не отменяет уже назначенные приёмы и не удаляет историю.
Показатели прививок относятся только к неархивным питомцам; старые сроки исключаются при наличии более новой
прививки с тем же названием без учёта регистра, как в сводке питомца. Прививки без срока не учитываются.
`vaccinationsDue` считает записи о прививках, а не питомцев.

Время фиксируется один раз на запрос; `today` определяется в часовом поясе клиники.
Горизонт берётся из `notification.vaccination-due.lead-days` (по умолчанию 7 дней).
Для одинакового времени ближайшего приёма выбирается запись с меньшим `id`.
Пустые показатели равны нулю. Данные ограничены текущим клиентом на уровне SQL.
Эндпоинт выполняет пять SQL-запросов независимо от количества питомцев, без выгрузки полной истории в память.
Существующие эндпоинты и их ответы сохраняются.

## Типичный сценарий записи на приём

1. `GET /api/v1/services?speciesId=...` — выбрать услугу для вида питомца; цена и длительность уже рассчитаны
   в `effectivePrice` и `effectiveDurationMin`.
2. `GET /api/v1/veterinarians` и `GET /api/v1/veterinarians/{id}/species` — выбрать врача, который лечит этот вид.
3. `GET /api/v1/work-schedules?veterinarianId=...` и `GET /api/v1/schedule-exceptions?veterinarianId=...` — посмотреть
   расписание врача.
4. `GET /api/v1/appointments/slots?speciesId=...&serviceId=...&from=...&to=...` — найти свободные слоты за период
   (даты клиники `from`–`to` включительно, не больше 14 дней). Каждый слот — `{startAt, endAt, veterinarianIds}`:
   какие врачи свободны в это время. С параметром `veterinarianId` ищутся слоты только этого врача. Длина слота равна
   длительности услуги для вида плюс буфер услуги, поэтому слот можно сразу передать в запись. Вместо поиска можно
   проверить конкретный слот через `GET /api/v1/appointments/availability`.
5. `POST /api/v1/client/appointments` — записаться. Запись создаётся в статусе `PENDING`, цену считает сервер.
6. Врач подтверждает и завершает приём через `PATCH /api/v1/veterinarian/appointments/{id}`.
7. При необходимости врач назначает повторный приём через `POST /api/v1/veterinarian/appointments/{id}/follow-ups`
   (тело: `startAt`, `endAt` и необязательный `serviceId` — по умолчанию услуга исходного приёма). Повторный приём
   создаётся к этому же врачу для того же питомца сразу в статусе `CONFIRMED`, ссылается на исходный через
   `followUpOf`, цену считает сервер. Исходный приём должен быть в статусе `CONFIRMED` или `COMPLETED`, а повторный —
   начинаться после его окончания.

Все обновления — `PATCH`: поля, отсутствующие в теле запроса, не меняются; явный `null` очищает nullable-поле.

Статусы записи: `PENDING → CONFIRMED | CANCELLED`, `CONFIRMED → COMPLETED | CANCELLED | NO_SHOW`.
`COMPLETED`, `CANCELLED` и `NO_SHOW` — конечные.

## Статистика (администратор)

Все эндпоинты — `GET /api/v1/admin/statistics/...` (группа `Admin: Statistics`) — принимают необязательные `from`
и `to`: даты клиники (ISO-8601, `2026-10-01`), обе включительно. Без дат берётся текущий месяц; если указана только
одна дата, вторая берётся из её месяца (`from=2026-11-15` → по `2026-11-30`). `from` не может быть позже `to`.
Запись попадает в период по времени начала приёма (`startAt`).

Выручка (`revenue`) — сумма цен записей в статусе `COMPLETED`; ожидаемая выручка (`expectedRevenue`) — `PENDING`
и `CONFIRMED`.

| Эндпоинт | Что возвращает |
|---|---|
| `/overview` | Сводка: `totalAppointments`, `appointmentsByStatus` (все статусы, включая нулевые), `revenue`, `expectedRevenue`, `averageCheck` (выручка / число завершённых), `cancellationRate` (`CANCELLED` / все), `noShowRate` (`NO_SHOW` / (`COMPLETED` + `NO_SHOW`)), `followUps` (повторные приёмы), `newClients`, `newPets` (созданы за период). Доли — от 0 до 1; `averageCheck` и доли равны `null`, если делить не на что |
| `/timeline?granularity=DAY\|WEEK\|MONTH` | Точки `{periodStart, appointments, completed, revenue}` по дням (по умолчанию), неделям (с понедельника) или месяцам, включая пустые. Считаются только записи внутри периода, поэтому первая и последняя неделя или месяц могут быть неполными |
| `/veterinarians` | По врачам, у которых есть записи за период: `{veterinarianId, fullName, appointments, completed, cancelled, noShows, revenue}` |
| `/services` | По услугам, у которых есть записи за период: `{serviceId, name, specializationName, appointments, completed, revenue}` |
| `/species` | По всем видам: `{speciesId, name, activePets, appointments, revenue}`; `activePets` — текущее число неархивных питомцев, от периода не зависит |

Списки отсортированы по выручке по убыванию, затем по имени.

## Уведомления

Уведомления хранятся на сервере; каждый пользователь видит только свои. Тексты `title` и `body` формируются на русском
в момент события (время — в часовом поясе клиники) и потом не меняются, даже если запись изменилась.

| Тип | Когда | Кому |
|---|---|---|
| `APPOINTMENT_BOOKED` | создана запись | врачу; если запись создал администратор — ещё и владельцу питомца |
| `APPOINTMENT_CONFIRMED` | запись подтверждена | владельцу |
| `APPOINTMENT_CANCELLED` | запись отменена | другой стороне: отменил клиент — врачу, врач — владельцу, администратор — обоим |
| `APPOINTMENT_RESCHEDULED` | администратор изменил время или врача | владельцу и врачу; при смене врача — и прежнему врачу |
| `APPOINTMENT_NO_SHOW` | отмечена неявка | владельцу |
| `FOLLOW_UP_SCHEDULED` | назначен повторный приём | владельцу |
| `APPOINTMENT_REMINDER` | за 24 часа до приёма в статусе `PENDING` или `CONFIRMED` (проверка каждые 5 минут) | владельцу, один раз на запись |
| `VACCINATION_DUE` | за 7 дней до даты ревакцинации (проверка ежедневно в 09:00) | владельцу неархивного питомца, один раз на прививку; не приходит, если питомцу уже сделали более позднюю прививку с тем же названием |

Автор действия уведомление о нём не получает; администраторы уведомлений не получают. Завершение приёма (`COMPLETED`)
и удаление записи уведомлений не создают. Сроки напоминаний и расписание проверок настраиваются в `application.yaml`
(`notification.*`).

REST (группа `Notifications`):

- `GET /api/v1/notifications?unreadOnly=&page=&size=` — постранично, новые сверху. Элемент: `{id, type, title, body,
  actorId, appointmentId, petId, vaccinationId, readAt, createdAt}`; `actorId` — кто совершил действие (`null` для
  напоминаний), `readAt = null` — не прочитано.
- `GET /api/v1/notifications/unread-count` — число непрочитанных.
- `POST /api/v1/notifications/{id}/read` — отметить прочитанным (уже прочитанное сохраняет `readAt`; чужое — `404`).
- `POST /api/v1/notifications/read-all` — отметить все; в `result` — сколько было непрочитанных.

Новые уведомления сразу приходят по WebSocket, протокол STOMP 1.2 (например, `@stomp/stompjs`):

1. Подключиться к `ws://<host>:8080/ws` (нативный WebSocket, без SockJS). Браузер не может передать токен при открытии
   соединения, поэтому он передаётся в кадре `CONNECT`: заголовок `Authorization: Bearer <accessToken>`.
2. Подписаться на `/user/queue/notifications`. Каждое сообщение — JSON того же вида, что элемент списка в REST.

Сервер только отправляет сообщения: подписка на другие адреса и отправка `SEND` отклоняются кадром `ERROR`, как и
`CONNECT` без действительного токена; после `ERROR` соединение закрывается. Токен проверяется при подключении, поэтому
открытое соединение продолжает работать и после истечения токена. Пока соединения нет, уведомления не теряются: после
подключения фронтенд берёт пропущенное из `GET /api/v1/notifications` и `unread-count`.

Для ручной проверки — `node chiron/scripts/stomp-listen.mjs --email <email> --password <пароль>` (Node 22+, без
зависимостей): подключается, подписывается и печатает полученные уведомления.

## Формат ответа

Любой ответ с телом обёрнут в `ApiResponse`:

```json
{
  "success": true,
  "result": { },
  "error": null,
  "timestamp": "2026-09-15T10:00:00Z"
}
```

При ошибке `success = false`, `result = null`, а в `error` лежат имя исключения, сообщение, HTTP-статус, путь запроса
и, для ошибок валидации, список нарушений по полям (`violations`).

Постраничные списки — `GET /api/v1/admin/{appointments,users,pets,vaccinations,schedule-exceptions}`,
`GET /api/v1/client/appointments`, `GET /api/v1/veterinarian/{appointments,vaccinations}` — принимают `page`
(с 0, по умолчанию 0) и `size` (1–100, по умолчанию 20), а в `result` возвращают страницу:

```json
{
  "items": [ ],
  "page": 0,
  "size": 20,
  "totalElements": 41,
  "totalPages": 3
}
```

`totalElements` — сколько записей подходит под фильтр всего, а не на текущей странице. Фильтры необязательны
и объединяются через AND; несколько статусов передаются повтором параметра: `?status=PENDING&status=CONFIRMED`.
Текстовые фильтры (`search`, `name`) ищут подстроку без учёта регистра. Публичные `GET /api/v1/services`
и `GET /api/v1/veterinarians` отдают только активные записи; все записи, включая неактивные, — в
`GET /api/v1/admin/services` и `GET /api/v1/admin/veterinarians`.

| Статус | Когда |
|---|---|
| `200` / `201` / `204` | Успех; `201` — при создании, `204` — при удалении (без тела) |
| `400` | Ошибка валидации или некорректный запрос |
| `401` | Нет токена, токен недействителен или истёк, неверный логин/пароль |
| `403` | Недостаточно прав или чужой ресурс |
| `404` | Сущность не найдена |
| `409` | Конфликт: такая запись уже существует или на неё ссылаются другие данные |
| `422` | Нарушено бизнес-правило (слот занят, питомец в архиве, врач не лечит этот вид и т. п.) |
| `503` | База данных недоступна |
